# Multi-port nodes

## Rationale

The [Web Audio API specification](https://webaudio.github.io/web-audio-api) allows a node to have an arbitrary [`numberOfInputs`](https://webaudio.github.io/web-audio-api/#dom-audionode-numberofinputs) or [`numberOfOutputs`](https://webaudio.github.io/web-audio-api/#dom-audionode-numberofoutputs). The native engine currently supports only a single input and a single output.

Because of that limitation, [`ChannelMergerNode`](https://webaudio.github.io/web-audio-api/#ChannelMergerNode) and [`ChannelSplitterNode`](https://webaudio.github.io/web-audio-api/#ChannelSplitterNode) are implemented as a workaround: several `AudioNode`s sit behind a single `ChannelMergerNodeHostObject` or `ChannelSplitterNodeHostObject` facade.

Also, implementation of [`AudioWorkletNode`](https://webaudio.github.io/web-audio-api/#AudioWorkletNode) is impossible, because it should allow a JS programmer to define an arbitrary [callback](https://webaudio.github.io/web-audio-api/#audioworkletprocess-callback-parameters), which should take `inputs` and `outputs` arguments as arrays.

## Required changes

### `HostGraph::Node`

Represent an edge endpoint by its owning node and a port index:

```cpp
struct HostGraph::Port {
  HostGraph::Node *node;
  std::uint32_t index;
};
using HostGraph::InputPort = HostGraph::Port;
using HostGraph::OutputPort = HostGraph::Port;
```

Change the node adjacency lists to:

```cpp
// diff-remove-start
std::vector<Node *> inputs;
std::vector<Node *> outputs;
// diff-remove-end
// diff-add-start
std::vector<std::vector<OutputPort>> inputs;
std::vector<std::vector<InputPort>> outputs;
// diff-add-end
```

A node can then have multiple input ports (as `ChannelMergerNode` does), and several outputs can connect to one input. [The specification defines the following mixing strategy](https://webaudio.github.io/web-audio-api/#input):

> For each input, an AudioNode performs a mixing of all connections to that input.

An edge is therefore identified by `(source node, source output, destination node, destination input)` tuple. Only an identical tuple is a duplicate; connecting different ports of the same node pair is valid.

### Graph operations

These operations need extra arguments for port indices; the rest of the API stays the same:

* `HostGraph`
    * `addNode()`, `removeNode()`, `addEdge()`, `removeEdge()`, ...
* `AudioGraph`
    * `addNode()`, ...
    * `AGEvent`s created in
        * `Graph`
        * `HostGraph`
* `HostNode`
    * `connect()`
    * `disconnect()`
    * ...

### InputPool

A single `std::uint32_t val` cannot represent a port. A port needs something like `(node id, adjacent edge id, input/output flag)`.

* One approach is to template `InputPool` so a slot can hold a wider value and more generic value.

    Currently, a slot has a size of 8 bytes for reasons related to memory and cache, therefore consequences of increasing it must be verified.

* The tuple can likely be packed into 32 bits, because graphs stay small.

### `AudioNode`

* Allocate the intended number of inputs and outputs in the constructor.

* Fix the **current spec inconsistency.** `AudioNode` currently updates the **output** buffer when setting the negotiated buffer during input up/down-mixing:

  ```cpp
  virtual void setNegotiatedBuffer(const std::shared_ptr<DSPAudioBuffer> &buffer) {
      setOutputBuffer(buffer);
  }
  ```

  The specification does not define a node's **output** channel count during this step. Each node chooses its own output policy, so negotiation must not change output width from outside the node. The up/down-mixing process refers to [`computedNumberOfChannels`](https://webaudio.github.io/web-audio-api/#computednumberofchannels), which defines the number of **input** channels.

  This works for most nodes because they share **one buffer** for input and output.

    * `StereoPannerNode` is a node that requires **distinct** input and output buffers. We can see that it actually updates the input buffer inside of `setNegotiatedBuffer()`. It wouldn't need to, if the base implementation refered to the input buffer in the first place.

* **Buffer policy.**
    * A node may have an arbitrary number of ports, and each port mahy have an arbitrary number of channels. Store those ports in a runtime-allocated array (for example `std::vector`).
    * Many nodes process frames in place on a single buffer, which is efficient, but that sharing is implicit. `AudioNode` should take a **constructor flag** that aliases `input[0]` and `output[0]` to the same buffer.

* **Up/down-mixing.** Run the mix independently for each port.

### Channel negotiation in `HostGraph.cpp`

Generalize the algorithm to operate on ports rather than nodes. That means iterating over every port in several places. One extra pointer dereference should not matter much for this path.

### `AudioNodeHostObject`

`getOutput()` and `getInput()` currently ignore the index argument and return a pointer to a node. They should honor the index and return a reference to a port.

## Open decisions

* Are there broader implications of refactoring `InputPool`?
* Is `NodeHandle` compatible with indexed ports?
* Define how each output port obtains its channel count. For most existing nodes it may mirror input 0, but merger, splitter, source, destination, and future multi-bus nodes need explicit rules.
* Review node options and constructor invariants. `numberOfInputs`/`numberOfOutputs` must be validated, immutable for the node lifetime, and used to allocate port storage before audio processing starts.
